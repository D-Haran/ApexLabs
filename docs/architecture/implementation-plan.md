# Initial milestone implementation plan

## Existing state

The workspace was empty: there was no source tree, build system, version-control metadata, or
legacy implementation to preserve.

## Decisions

1. **Dependency-light build.** CMake and the C++ standard library are sufficient. Tests use a
   small deterministic harness so initial builds do not depend on network package fetching.
2. **Library-first boundary.** Physics, integration, simulation orchestration, configuration, and
   telemetry serialization live in `apexlab_sim_core`; the CLI is only an adapter.
3. **Typed scalar quantities.** Public state and parameter structures use distinct wrappers for
   time, distance, velocity, acceleration, mass, and force. This prevents accidental interchange
   without introducing a third-party units dependency.
4. **Signed 1D convention.** Positive position and velocity are forward. Drive force is positive;
   drag, rolling resistance, and braking oppose motion. A zero-speed event prevents braking from
   numerically reversing the vehicle.
5. **Fixed-step integration.** Euler exists as a transparent baseline. Classical RK4 is the
   default because it provides substantially lower truncation error for smooth dynamics without
   yet introducing adaptive-step complexity.
6. **Configuration and provenance.** JSON Schema is the canonical parameter contract. The C++
   loader accepts the documented schema and validates finite values/ranges. Generic and
   analytical fixtures explicitly label their sources as assumptions or analytical fixtures.
7. **Telemetry contract.** CSV schema version 1 is intentionally simple, inspectable, and replayable
   without running physics. Each row includes time, step, state, controls, and the exact force
   decomposition used for acceleration.
8. **Black-box validation.** Python launches the compiled CLI, reads its CSV, compares it with
   closed-form results, writes numeric summaries, and produces SVG plots using only the standard
   library.

## Work sequence

1. Scaffold targets and public interfaces.
2. Implement configuration, force model, integrators, simulation runner, and CSV writer.
3. Add CLI and deterministic tests.
4. Build with strict compiler warnings and run CTest.
5. Run analytical experiments and convergence studies.
6. Record measured results, benchmark output, and current limitations.

## Acceptance criteria

- Clean configure/build with a C++20 compiler.
- All CTest cases pass deterministically.
- Constant-force, drag coast-down, and constant-deceleration results are compared to analytical
  values with reported errors.
- Decreasing timestep produces the expected convergence trend.
- A CSV generated by the CLI contains enough state to replay the longitudinal motion.
- Documentation contains no unmeasured performance or fidelity claims.
